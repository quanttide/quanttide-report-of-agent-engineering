# 量潮 AGENTS.md 报告：被反复抄写的三类规范，还停在「提醒」，没进入「约束」

> 生成日期：2026-10-11
> 数据来源：46 个领域仓 22811 条候选片段的全量近重复检测
> 样本口径：AGENTS.md 贡献 375 条片段，占语料 1.64%；其中 36 条卷入近重复，富集 2.31 倍
> 结论：**重复的不是文件，是三类规范。而 17 条规范里 15 条只有文字、没有任何东西在判——它们散在 2 到 7 个地方，恰恰说明这些规矩还没生效。**

---

## 前言

**背景。** 我们在 46 个领域仓上跑了一遍近重复检测——把每一段话变成向量，找出讲同一件事的两处。全语料 22811 条片段，946 条（4.1%）卷进近重复；其中真正要人处理的只有 41 组。

第一版按**文件**数，得到「AGENTS.md 涉及 16 组重复」——那个数没法指挥行动。第二版改成按**规范**数：同一条规矩到底写在几个地方、写得一不一样。数出 17 条，四簇。**这一版再往下追一层：这些规范为什么非得写这么多遍。**

**方法。** 本地 bge-m3 向量化（1024 维），余弦 ≥ 0.90 算近重复。再拿规范名去全语料探针，逐条看散布几个域、措辞有没有分岔，并逐组算同一组内的文字相似度。全程离线，没花 API 钱。数字都可复算。

**立场。** 我们本来想验证 AGENTS.md 是不是「没人管、各写各的」的角落。**不是。它是规矩最密集、也抄得最勤的地方**——而抄得勤，恰恰是规矩没生效的症状。这份报告写给维护这些仓的人，也写给以后往仓里派智能体的人。

---

## 一、反复抄写的是哪些规范

17 条，四簇。

### 第一簇：人机协作纪律——散得最广

    最小干预     6 域    agent algorithm asset code connect growth
    原子提交     7 域    algorithm code connect execute growth human pay
    提交即推送   5 域    agent algorithm code connect growth
    信息复用     5 域    algorithm code connect growth meta
    维护记录     4 域    algorithm code connect growth

**注意这五条其实是一段。** 它们本来就是同一份「人机协作范式」的五个要点，被拆散在 6 到 7 个域里各写一份。connect 那版还自己加了两条（**查询契约**、**验证优先**），只有它有。

一段纪律被复制到 7 个域——这不算「七条规矩各自重复」，**是一条规矩重复了七次。**

### 第二簇：仓库结构约定

    目录结构 apps / packages / examples      5 域   connect devops product strategy support
    子模块提交顺序                            2 域   code think（另有仓内重抄）
    聚合仓库自我介绍句                        2 域   algorithm code
    工具箱职责声明（只做表达，不定义领域）      2 域   code work（另有仓内重抄）

### 第三簇：写作与命名规矩

    措辞严格使用既有术语 ＋ 决策四段式 ＋ 待决事项不进 TODO     2 域   credit work
    决策文件命名（英文小写连字符、不带头日期）                   2 域   auth pay

第三簇那三句也是连在一起出现的，算一条。

### 第四簇：领域自己的纪律——只在域内重抄，没出过域

    契约优先                          asset   根 ↔ apps/qtcloud-asset
    fixtures 先行 / 禁止端侧发明语义    pay     根 ↔ packages/quanttide-pay-toolkit/packages/go 等

这一类**没有跨域**——它只在同一个仓里，从根目录往子目录重抄了一遍。

## 二、已经抄岔的地方

重复本身不致命，**抄的次数够多就会分岔**。已经发生的：

**人机协作范式**（7 个域）——同一个「提交即推送」要点，两种说法并存：

    提交后默认推送到远端，除非用户明确说「只提交不推」
    vs
    修改完成后直接提交并推送到远端，无需另行请示，除非用户明确说「只提交不推」

同一段还抄出了三种排版：`-` 列表、`1. **` 编号、直角引号与直引号混用；条数一版 5 条、一版 6 条。

**目录结构约定**（5 个域）——三种写法：

    一份   data/ · docs/ · apps/ · packages/ · examples/
    一份   apps/ · packages/toolkit · examples/<域>-lab · docs/
    一份   应用模式（完整的可部署应用）· 库模式（可复用的库）

**决策文件命名**（auth / pay）——按 Record 与 Report 的严格划分，**必有一处错**：

    auth   决策记录文件用英文命名（小写连字符），不带头日期
    pay    决策报告文件用英文命名（小写连字符），不带头日期

**措辞与决策写法**（credit / work）——work 版短了一截：

    credit  措辞严格使用既有术语，不用口语。决策思路写在开发者文档里，按「背景 / 选项 / 影响 / 建议」
            梳理清楚；不用「要你拍板」这类说法把决策推给用户。待决事项不进 `TODO.md`，TODO 只列可直接动手的事项。
    work    措辞严格使用既有术语，不用口语。决策思路写在开发者文档里，按「背景 / 选项 / 影响 / 建议」梳理清楚。

**工具箱职责声明**（code / work）——code 版少一句「收进来的每一样都要能在规格里找到出处」。

**子模块提交顺序**（code / think）——三种写法。

**一句话收这一节**：17 条规范里，**已经 6 条各抄出了两种以上版本**。读者（尤其是智能体）拿到哪一份，就按哪一份干。

---

## 三、原因推测

三条，一条比一条根本。

**第一，规矩没有下发渠道，只能靠复制传播。**

仓库族里没有「一处写、处处生效」的机制。想让每个仓都守住同一条纪律，只能到每个仓里写一遍。**复制是最省事、也是唯一可用的传播方式。**

**第二，复制沿着两条轴发生，仓内那条更隐蔽。**

横轴（域 ↔ 域）看得出来，跨域本来就显眼——第一、二、三簇全在这条轴上。竖轴（仓 ↔ 子目录）不容易发现，同一仓里的父子文件抄一遍几乎不引人注意——第四簇就在这条轴上，**我们过去根本没盯过**。

**第三，越抽象的内容越容易被复制。**

抽象的话在哪都成立，所以在哪都得说一遍；具体的内容只说一次。这解释了富集分布：AGENTS.md **2.31 倍** > 章程 2.3 倍 > index.md 1.6 倍 > 普通正文 **0.88 倍（低于平均）**。**不是门面文件疏于维护，是它们本来就该到处出现。**

## 四、再往下一层：这些规矩还停在「提醒」，没进入「约束」

上面三条解释了「为什么散」。还有一层更根本的：**这些规矩本身没生效，所以只能靠一遍遍说。**

### 17 条里只有 2 条有落点

规矩「有落点」的意思是——**有一个东西在判，不靠读到的人自觉。**

唯一做到的，是 pay 那两条：

    packages/quanttide-pay-toolkit/tests/fixtures/{ledger,money,status}.json    ← 契约权威在这
    packages/quanttide-pay-toolkit/packages/go/contracttest/contract_test.go    ← 有东西在判

它写的是「实现与 fixtures 不一致 = 失败」「未知渠道码必须报错而非 UNKNOWN 兜底」——**这不是祈使句，是有裁判的。**

其余 15 条全是「请照做」：「最小干预」「原子提交」「措辞严格使用既有术语」「决策文件用英文命名」……**没有一条有东西在判，全靠读到的人自觉。**

**一条规矩要写在 2 到 7 个地方才有人守，它本身就没生效。** 生效的规矩只需说一次，或者根本不用写。

### 但要诚实：分叉跟落点无关

我们本来想顺着说「有落点就不分叉」——**数据打脸了**。同一组内的文字相似度（取最低值）：

    pay · fixtures 先行          0.854    有落点
    pay · 禁止端侧发明语义        0.686    有落点   ← 比有些纯文字的还低
    asset · 契约优先             0.848    有落点
    目录结构                    0.954    纯文字   ← 纯文字却最一致
    子模块提交顺序               0.923    纯文字
    措辞用既有术语               0.743    纯文字
    决策文件命名                 0.618    纯文字
    人机协作范式                 0.548    纯文字   ← 最岔

pay 那两条有裁判，**文字照样在仓内抄了两遍**。

### 所以是两件事

| | 管什么 | 现状 |
|:--|:--|:--|
| **固化** | 规范会不会被执行 | **15 / 17 条没做到**，只有文字 |
| **传播** | 规范要不要写 N 遍 | **17 / 17 条没做到**，没有下发渠道 |

两个问题叠在一起，就是现在这张脸：**同一条没生效的规矩，被抄到 7 个地方，抄出了三个版本。**

## 五、理想状况

理想状态不是「没有重复」——**规矩本来就该在每个用到它的地方出现，不然读者得跳出去看。** 理想状态要两层同时成立：

**其一，规矩有落点——能进机器的进机器，不靠人自觉。**
**其二，副本是生成的——一处算数，别处的副本由脚本产出，不手抄。**

两条判据，切法不同：

> **收正本判据**：一条规矩，换掉领域名之后一字不差地成立，它就该收一份正本；
> 只在某个域里才说得通的，它就该留在那个域。
>
> **给落点判据**：一条规矩，如果违反它会被某个东西拦下来（测试、hook、CI、脚手架），
> 它就算固化了；只能靠「读到的人自觉」，它就还停在提醒。

---

## 六、改进建议

不再一刀切说「收一份正本」——**先问能不能给落点，再谈收不收正本。**

### 已经进机器的——保持，别动

    pay 的 fixtures 先行 / 禁止端侧发明语义
    → 已经是约束。只剩仓内那份重抄可以删。

### 能进机器的——优先做，这是真固化

| 规范 | 落点 |
|:--|:--|
| 原子提交 / 提交即推送 | git hook（暂存区范围检查、提交后自动推送） |
| 子模块提交顺序 | 释放 / 更新脚本 |
| 决策文件命名 | 决策文档模板 ＋ CI 检查文件名 |
| 决策四段式 | 决策文档模板 |
| 目录结构约定 | 仓脚手架 |
| 工具箱职责声明 | 仓库模板 ＋ CI 检查 |

这些做完，规范就从「请照做」变成「违反不了」。

### 进不了机器的——收正本，副本用脚本注入

    最小干预 · 信息复用 · 措辞用既有术语 · 待决事项不进 TODO

这类靠文字是没办法的事。各仓 AGENTS.md 里留一段带标记的区间，由脚本从正本注入——**复制可以继续，但必须是生成的。**

### 放错位置的——挪回它该在的那层

**「最小干预 / 信息复用 / 提交即推送」是关于智能体的规矩，不是关于某个仓的规矩。**

它散在 7 个域各写一遍，恰恰说明它没写在该在的地方——它该固化在**智能体被驱动的那一层**（工具审批、权限、默认行为），而不是散在 46 个仓的说明书里。

**它不是重复了七次，是被放错了位置。**

### 子目录那份——直接删

    asset 的契约优先、pay 的 fixtures 先行 / 禁止端侧发明语义
    → 父目录已经说过的话，子目录不必再说。不用上升、不用收正本。

### 谁定正本

**我们只指出「同一条规矩现在散在哪些仓、写成了几个样子」；哪份为准是领域的事。** 建议由各自领域的章程或规格来定，不由这份报告定。

---

## 结论

**被反复抄写的是三类规范——一段人机协作纪律（散 7 个域）、一套仓库结构约定（散 5 个域）、一组写作命名规矩（散 2–3 个域）；另有一类领域自己的纪律只在仓内重抄。17 条里已经 6 条抄岔。**

**但根子不在「抄得不整齐」，在于这些规矩大多还没生效**：17 条里只有 2 条有东西在判，其余只有文字。**没生效的规矩只能靠一遍遍说，说得多了就分岔。**

**治法是三句话：能进机器的进机器（hook / CI / 脚手架 / 模板）；进不了机器的收一份正本、副本由脚本生成；放错位置的挪回它该在的那层。**

顺带一句：我们本来想找「没人管的角落」，找到的却是「**管得太多、到处都管了一遍**」的地方。这两件事的解法完全相反。
