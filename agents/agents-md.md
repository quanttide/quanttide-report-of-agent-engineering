# 量潮 AGENTS.md 报告：被反复抄写的是三类规范，两类已经抄岔

> 生成日期：2026-10-11
> 数据来源：46 个领域仓 22811 条候选片段的全量近重复检测
> 样本口径：AGENTS.md 贡献 375 条片段，占语料 1.64%；其中 36 条卷入近重复，富集 2.31 倍
> 结论：**重复的不是文件，是三类规范——一段人机协作纪律、一套仓库结构约定、一组写作命名规矩。前两类已经抄出多种版本。**

---

## 前言

**背景。** 我们在 46 个领域仓上跑了一遍近重复检测——把每一段话变成向量，找出讲同一件事的两处。全语料 22811 条片段，946 条（4.1%）卷进近重复；其中真正要人处理的只有 41 组。

上一版报告是按**文件**数的，得到一句「AGENTS.md 涉及 16 组重复」。那个数没法指挥行动——知道有 16 组重复，你还是不知道该改哪句话。**这一版改成按规范数：同一条规矩到底写在几个地方、写得一不一样。** 数出来 17 条，四簇。

**方法。** 本地 bge-m3 向量化（1024 维），余弦 ≥ 0.90 算近重复。再拿规范名去全语料探针，逐条看散布几个域、措辞有没有分岔。全程离线，没花 API 钱。数字都可复算。

**立场。** 我们本来想验证 AGENTS.md 是不是「没人管、各写各的」的角落。**不是。它是规矩最密集、也抄得最勤的地方。** 把这一点说准，比多找几组重复有用。这份报告写给维护这些仓的人，也写给以后往仓里派智能体的人。

## 一、反复抄写的是哪些规范

17 条，四簇。

### 第一簇：人机协作纪律——散得最广

    最小干预     6 域    agent algorithm asset code connect growth
    原子提交     7 域    algorithm code connect execute growth human pay
    提交即推送   5 域    agent algorithm code connect growth
    信息复用     5 域    algorithm code connect growth meta
    维护记录     4 域    algorithm code connect growth

**注意这五条其实是一段。** 它们本来就是同一份「人机协作范式」的五个要点，被拆散在 6 到 7 个域里各写一份。connect 那版还自己加了两条（**查询契约**、**验证优先**），只有它有。

一段纪律被复制到 7 个域——这不算「七条规矩各自重复」，**是一条规矩重复了七次。**

### 第二簇：仓库结构约定

    目录结构 apps / packages / examples      5 域   connect devops product strategy support
    子模块提交顺序                            2 域   code think（另有仓内重抄）
    聚合仓库自我介绍句                        2 域   algorithm code
    工具箱职责声明（只做表达，不定义领域）      2 域   code work（另有仓内重抄）

### 第三簇：写作与命名规矩

    措辞严格使用既有术语 ＋ 决策四段式 ＋ 待决事项不进 TODO     2 域   credit work
    决策文件命名（英文小写连字符、不带头日期）                   2 域   auth pay

第三簇那三句也是连在一起出现的，算一条。

### 第四簇：领域自己的纪律——只在域内重抄，没出过域

    契约优先                          asset   根 ↔ apps/qtcloud-asset
    fixtures 先行 / 禁止端侧发明语义    pay     根 ↔ packages/quanttide-pay-toolkit/packages/go 等

这一类**没有跨域**——它只在同一个仓里，从根目录往子目录重抄了一遍。

## 二、已经抄岔的地方

重复本身不致命，**抄的次数够多就会分岔**。已经发生的：

**人机协作范式**（7 个域）——同一个「提交即推送」要点，两种说法并存：

    提交后默认推送到远端，除非用户明确说「只提交不推」
    vs
    修改完成后直接提交并推送到远端，无需另行请示，除非用户明确说「只提交不推」

同一段还抄出了三种排版：`-` 列表、`1. **` 编号、直角引号与直引号混用；条数一版 5 条、一版 6 条。

**目录结构约定**（5 个域）——三种写法：

    一份   data/ · docs/ · apps/ · packages/ · examples/
    一份   apps/ · packages/toolkit · examples/<域>-lab · docs/
    一份   应用模式（完整的可部署应用）· 库模式（可复用的库）

**决策文件命名**（auth / pay）——按 Record 与 Report 的严格划分，**必有一处错**：

    auth   决策记录文件用英文命名（小写连字符），不带头日期
    pay    决策报告文件用英文命名（小写连字符），不带头日期

**措辞与决策写法**（credit / work）——work 版短了一截：

    credit  措辞严格使用既有术语，不用口语。决策思路写在开发者文档里，按「背景 / 选项 / 影响 / 建议」
            梳理清楚；不用「要你拍板」这类说法把决策推给用户。待决事项不进 `TODO.md`，TODO 只列可直接动手的事项。
    work    措辞严格使用既有术语，不用口语。决策思路写在开发者文档里，按「背景 / 选项 / 影响 / 建议」梳理清楚。

**工具箱职责声明**（code / work）——code 版少一句「收进来的每一样都要能在规格里找到出处」。

**子模块提交顺序**（code / think）——三种写法：「修改后先提交推送本仓」「修改规范后先提交推送本仓」「修改后：先提交推送本仓」。

**一句话收这一节**：17 条规范里，**已经 6 条各抄出了两种以上版本**。读者（尤其是智能体）拿到哪一份，就按哪一份干。

## 三、原因推测

三条，一条比一条根本。

**第一，规矩没有下发渠道，只能靠复制传播。**

仓库族里没有「一处写、处处生效」的机制。想让每个仓都守住同一条纪律，只能到每个仓里写一遍。**复制是最省事、也是唯一可用的传播方式。**

**第二，复制沿着两条轴发生，仓内那条更隐蔽。**

横轴（域 ↔ 域）看得出来，跨域本来就显眼——第一、二、三簇全在这条轴上。竖轴（仓 ↔ 子目录）不容易发现，同一仓里的父子文件抄一遍几乎不引人注意——第四簇就在这条轴上，**我们过去根本没盯过**。

**第三，越抽象的内容越容易被复制。**

抽象的话在哪都成立，所以在哪都得说一遍；具体的内容只说一次。这解释了富集分布：AGENTS.md **2.31 倍** > 章程 2.3 倍 > index.md 1.6 倍 > 普通正文 **0.88 倍（低于平均）**。**不是门面文件疏于维护，是它们本来就该到处出现。**

## 四、理想状况

理想状态不是「没有重复」——**规矩本来就该在每个用到它的地方出现，不然读者得跳出去看。** 理想状态是：

**同一件事只有一处算数，别处出现的是它的副本，而且副本是生成的，不是手抄的。**

切这一刀只用一条判据：

> **一条规矩，换掉领域名之后一字不差地成立，它就该收一份正本；
> 只在某个域里才说得通的，它就该留在那个域。**

按这条判据，17 条规范分成三档，处理方式各不相同。

## 五、改进建议

### 第一梯队——散 5 域以上、且已分叉，必须收正本

| 规范 | 散布 | 已经分岔成 |
|:--|:--|:--|
| 人机协作范式（5 个要点） | 6–7 域 | 两种说法 · 引号直角/直混用 · 条数 5/6 |
| 目录结构约定 | 5 域 | 三种写法 |

**做法**：各收一份正本，其余域引用。通用块**用脚本注入，不用手抄**——各仓 AGENTS.md 里留一段带标记的区间，改正本一处、重新注入即可。**复制可以继续，但必须是生成的。**

### 第二梯队——散 2 域、已分叉，直接统一即可

| 规范 | 散布 | 已经分岔成 |
|:--|:--|:--|
| 决策文件命名 | auth / pay | 记录 vs 报告（必有一错） |
| 措辞与决策写法 | credit / work | 一份短一截 |
| 工具箱职责声明 | code / work | 一份少尾句 |
| 子模块提交顺序 | code / think | 三种写法 |

量小，不必建工具。

### 第三梯队——只在域内纵向重抄，还没分叉，最好办

    asset 的契约优先
    pay 的 fixtures 先行 / 禁止端侧发明语义

**做法**：父目录已经说过的话，子目录删掉。**不用上升、不用收正本**——那是各域自己的纪律，留在域里是对的。

### 预期效果

17 条规范收成 **6 份正本**（人机协作范式、目录结构、决策文件命名、措辞与决策写法、工具箱职责声明、子模块提交顺序），加 2 处子目录删重。跨域的重抄和仓内的重抄同时归零。

### 谁定正本

**我们只指出「同一条规矩现在散在哪些仓、写成了几个样子」；哪份为准是领域的事。** 建议由各自领域的章程或规格来定，不由这份报告定。

---

## 结论

**被反复抄写的是三类规范——一段人机协作纪律（散 7 个域）、一套仓库结构约定（散 5 个域）、一组写作命名规矩（散 2–3 个域）；另有一类领域自己的纪律只在仓内重抄。17 条里已经 6 条抄岔。**

**治它的办法不是「少写几遍」，而是：能换掉领域名还成立的，收一份正本、副本用脚本生成；只在某个域说得通的，留在域里，子目录别重抄父的。**

顺带一句：我们本来想找「没人管的角落」，找到的却是「**管得太多、到处都管了一遍**」的地方。这两件事的解法完全相反。
